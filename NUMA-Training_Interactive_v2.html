Start here

Your server is fast.
Your packets are slow.

This is a training about one specific reason that happens — and it is a reason that never shows up in a log file.

The problem in plain English

You buy a 100 gigabit network card. You put it in a powerful server. You run your software. You measure 40 gigabits.

Nothing crashed. Nothing errored. No alarm fired. The card is fine, the software is fine, and the server is fine. They just disagree about where in the machine the work should happen — and that disagreement is expensive.

That disagreement has a name: NUMA.

What you will be able to do by the end

  • Explain what NUMA is to someone else, in one or two sentences.
  • Find out which part of a server your network card is attached to, with one command.
  • Recognise the four or five settings that most often get this wrong.
  • Follow a checklist that puts the card, the memory and the processor cores in the same place.

Module 1

What NUMA actually is

In one minute

A modern server is not one big pool of memory. It is several smaller pools, each one bolted to a specific group of processor cores.

A core can reach any pool. But reaching its own pool is fast, and reaching someone else's pool means crossing a link inside the machine — which is slower and has limited capacity.

That is it. That is NUMA: Non-Uniform Memory Access. Memory access is not uniform, because where the memory sits matters.

Why servers are built this way

It would be simpler to have one pool of memory shared equally by everything. Older, smaller servers worked exactly like that.

The problem is that a single shared pool becomes a traffic jam. Every core wants memory at once, and they all queue for the same path to it. Adding more cores stops helping.

So chip designers split memory into groups and gave each group its own path. Now many cores can fetch memory at the same time instead of taking turns. The Linux kernel documentation puts the motive bluntly: this architecture is "a means to provide scalable memory bandwidth."1

The catch, and it is the whole point of this training

That extra speed is conditional. The same documentation says it only materialises if software arranges for the large majority of memory requests to go to local memory.1

NUMA is a deal. The hardware offers you more total speed. In exchange, you have to keep work near its data. Skip your side of the deal and you get the complexity with none of the benefit.

Local and remote, side by side

Below, each box is a NUMA node — one group of cores with its own memory. Watch the two dots. The green one stays home. The red one has to cross.

Two things to take from that picture.

First: the red trip still works. Remote memory is not broken or forbidden — it is just slower. Nothing fails, so nothing warns you. That is why this problem hides so well.

Second: notice the expansion slots at the bottom of each node. A network card plugged into node 0 belongs to node 0. This becomes important in Module 5.

Go deeper — how the Linux kernel defines all thisAdvanced

The kernel documentation answers "what is NUMA" from two angles.

The hardware view. A NUMA system is built from multiple assemblies, each of which may contain zero or more CPUs, local memory, and/or I/O buses. The docs call these assemblies cells. Cells are joined by a system interconnect — typically a crossbar or point-to-point links — and those can be aggregated so cells sit at multiple distances from each other, not merely "near" and "far."1

The software view. Linux divides hardware into abstractions called nodes and maps nodes onto physical cells, hiding some architectural detail. A node may contain zero or more CPUs, memory, and/or I/O buses.1

The platforms Linux targets are cache-coherent NUMA (ccNUMA): all memory is visible and accessible from any CPU on any cell, and coherency is handled in hardware by the processor caches and/or the interconnect.1 That hardware guarantee is precisely why remote access is merely slow rather than impossible.

The x86 exception worth knowing

On some architectures — x86 included — Linux will hide a node representing a cell with no attached memory, and reassign that cell's CPUs to a node that does have memory. The documented consequence: you cannot assume that all CPUs Linux associates with a given node see the same local memory access times and bandwidth.1

Module 2

Speed has two meanings

In one minute

When people say memory is "fast," they mean one of two different things, and NUMA affects both.

  • Latency — how long one request takes. Like how long a single delivery takes to arrive.
  • Bandwidth — how much data moves per second. Like how many deliveries you can make per hour.

Going remote hurts latency because the trip is longer. It hurts bandwidth for a different and less obvious reason: everything remote has to squeeze through one shared link.

Why bandwidth is the one that surprises people

Your memory is not one pipe. It is several parallel pipes, called channels. A server might have eight of them. The memory controller can use all eight at the same time, which is where the big numbers on the spec sheet come from.

Think of supermarket checkouts. Eight open tills serve eight customers at once. That is your local memory.

Now imagine those eight tills are in a different building, and everyone has to walk through one connecting corridor to reach them. The tills did not get slower. The corridor is the limit now. That corridor is the link between NUMA nodes.

Try it

The rule that follows from this

An empty channel gives you nothing. If your server has eight memory channels but memory sticks in only four of them, you have thrown away half your bandwidth before any software runs. The DPDK documentation says to make sure every memory channel has at least one memory stick in it, and calls this one of the most direct effects on performance.7

More total speed is not more speed for you

This is the single most useful idea in this module.

A two-processor server has roughly twice the memory channels of a one-processor server. That is twice the total bandwidth for the machine. It is not twice the bandwidth for any one piece of software.

A program running on one node only gets that node's channels. Adding a second processor does not widen its path. If that program then starts reaching across to the other node's memory, you have added a long trip without adding any speed. It can end up slower than the smaller server.

Go deeper — effective bandwidth, ranks, and what actually sets the ceilingAdvanced

The kernel documentation is careful with its wording: it says "effective memory bandwidth", not peak bandwidth.1 Peak bandwidth is a datasheet property — channel count times transfer rate times bus width. Effective bandwidth is what one thread, on one core, touching one address range, actually gets. On a NUMA machine the two can differ by a large factor, and nothing reports when they do.

FactorWhat it controlsHow it fails
1 · Channel parallelism Memory controllers have several channels that load and store in parallel; the count and distribution vary by controller and configuration.6 "Each channel has a bandwidth limit, meaning that if all memory access operations are done on the first channel only, there is a potential bottleneck."6
2 · Physical population DPDK: ensure each memory channel has at least one DIMM inserted, at least 4 GB each.7 Flagged as having "one of the most direct effects on performance."7
3 · Interleave scope How many channels one node's address space spreads across. On AMD, the NPS setting controls the interleave pattern within a node, and the number of channels interleaved decreases as the NPS setting gets higher.5 On Intel, UMA interleaves across all controllers while an SNC domain maps to its own controller and channels.11 Narrower domains cut latency and cut the channel count any one node can reach. This is the central trade, not a free win.
4 · Interconnect ceiling Anything remote is capped by the link, not by memory. AMD: up to 4 xGMI links at up to 32 Gbps, each using up to 16 PCIe lanes.5 Intel: up to 4 UPI links per processor, x24 wide, up to 16 GT/s.11 Fixed, shared and finite. Packets, cache-coherency traffic and page-table lookups all compete for it.
Ranks — the second-order term

Below channels sit ranks. Critically, "the ranks cannot be accessed simultaneously since they share the same data path," and the physical layout of memory chips on the module does not necessarily relate to the rank count.10 This is why DPDK's mempool library pads objects so each starts on a different channel and rank — spreading addresses so all channels stay equally loaded.610 Effective bandwidth depends on your access pattern, not only your hardware.

Derived arithmetic — not a vendor claim

Everything else here is cited. This paragraph is not, because it is a queueing identity rather than a documented fact. Sustained bandwidth equals outstanding requests divided by latency. If latency rises on the remote path while the number of requests a core can keep in flight stays fixed, bandwidth falls even when no link is saturated. That is why cross-node placement can cost throughput on a system whose link utilisation graphs look comfortable. Verify it on your own platform rather than taking it on faith.

Module 3

Seeing NUMA on a real machine

In one minute

Linux numbers the nodes: node 0, node 1, and so on. A handful of commands show you the layout.

By default Linux tries to give a program memory from the node its core is running on. This is called local allocation, and it usually works.

It stops working when the program's threads get moved to another node by the scheduler, because their memory does not move with them. This is the main reason performance-critical software pins its threads to specific cores.

The commands worth knowing

# How many nodes, which cores in each, and how far apart they are
numactl --hardware

# A full picture: cores AND expansion cards, grouped by node [5]
lstopo-no-graphics

# The single most useful file in this whole training.
# Tells you which node a specific card belongs to. [5][7]
cat /sys/bus/pci/devices/0000:85:00.0/numa_node

That last one prints a number — 0, 1, and so on. That number is the node your network card lives in. Almost everything else in this training follows from it.

Why pinning matters

Linux tries to keep a program near its memory. But the kernel documentation is explicit that the scheduler does not take a task's NUMA footprint into account directly. Under enough load imbalance, tasks migrate to other nodes — away from the memory that was allocated for them.1

The memory stays put. The thread does not. From that moment on, every access is a remote access. Pinning a thread to a core stops this from happening.

Go deeper — zonelists, fallback, and NUMA memory policyKernel internals

Per-node memory management

  • For each node with memory, Linux builds an independent memory management subsystem: its own free page lists, in-use lists, usage statistics and locks.1
  • For each memory zone (DMA, DMA32, NORMAL, HIGH_MEMORY, MOVABLE) Linux constructs an ordered zonelist — the sequence of zones and nodes to visit when the chosen zone cannot satisfy an allocation. That situation is called overflow or fallback.1
  • Linux defaults to a node-ordered zonelist: fall back to other zones on the same node before reaching for remote nodes, which are then ordered by NUMA distance.1

Memory policy — the programming interface

Memory policy determines which node the kernel allocates from. It is a programming interface for NUMA-aware applications; cpusets are the separate administrative mechanism for restricting nodes. When both apply to a task, the cpuset restrictions take priority.2

ModeBehaviour
MPOL_BINDMemory must come from the specified node set; allocated from the node in the set with sufficient free memory that is closest to the allocating node.2
MPOL_PREFERREDTry the single specified node; on failure search others in order of increasing distance, using platform firmware distance data.2
MPOL_INTERLEAVEInterleave allocations at page granularity across the specified nodes.2
MPOL_PREFERRED_MANYPrefer a node set; under pressure on all of them, fall back to all existing nodes.2
MPOL_WEIGHTED_INTERLEAVEWeighted interleave via /sys/kernel/mm/mempolicy/weighted_interleave/ — nodes [0,1] weighted [5,2] places 5 pages on node0 per 2 on node1.2
Two scoping details

A task policy applies only to pages allocated after the policy is installed — pages already faulted in stay where they are.2 And VMA policies apply only to anonymous pages, are shared across threads, and are not inheritable across exec(), so only NUMA-aware applications can use them.2 Setting policy after your memory pools are built achieves nothing.

Administrators restrict migration using taskset(1), numactl(1) and sched_setaffinity(2), and change allocation behaviour using memory policy. Control groups and cpusets bound what an unprivileged user may request.1

Module 4

Your chip's NUMA layout is a setting, not a fact

In one minute

Here is the part most people do not expect. How many NUMA nodes your processor has is configurable in the server's BIOS. The same physical chip can present itself as one node, two, four, or more.

The trade-off is consistent across both vendors:

  • More nodes = shorter distances inside each node = lower latency. But each node has fewer memory channels, so less bandwidth each.
  • Fewer nodes = more channels per node = more bandwidth. But longer average distances.

And the part that matters most for networking: this setting changes which node your network card belongs to. Change it, and you must re-check everything.

AMD calls it NPS

AMD's setting is NPS — NUMA Nodes Per Socket. Click through the options to see the chip divided up different ways. The dashed outlines are the NUMA nodes.

Intel calls it Sub-NUMA Clustering

Intel's equivalent is SNC. Intel also offers two middle options — Hemisphere and Quadrant — that get some of the benefit without the software needing to know anything about it.11

Do not "fix" this by turning NUMA off

Both vendors offer a setting that presents the whole chip — or on AMD, the whole server — as a single node. It is tempting, because the warnings go away.

They go away because you removed the reporting, not the distance. The links are still there and the trips are still long. Your software just lost the ability to see them and avoid them. On AMD's NPS=0 the memory of both processors is interleaved into one address space, so roughly half of any allocation sits on the far side of the machine, invisibly.5

A safe default if you are unsure

AMD lists NPS=4 as preferred for low latency and I/O throughput.5 For Intel, if you cannot guarantee your software is NUMA-aware, Quadrant is the BIOS default and needs no software changes.11 Then measure — this training gives you the tools, not a universal answer.

A trade-off not printed on the datasheet

Because these processor-to-processor links share the physical connections used by PCIe lanes, a system designer can drop from 4 links to 3 and reclaim lanes — allocating up to 160 lanes for PCIe (80 per socket) by using 48 lanes per socket for links instead of 64.5 More slots for network cards, less processor-to-processor bandwidth.

What each NPS value does

  • NPS=4 — four nodes per socket, each quadrant its own domain with 3 CCDs, 3 UMCs and 1 I/O hub. Memory interleaves across that quadrant's channels. PCIe devices are local to one of the four domains depending on which quadrant carries the device's root complex.5
  • NPS=2 — two domains, half the cores and half the channels each; memory interleaves across the six channels in each domain.5
  • NPS=1 — one node per socket. All channels, all cores, all PCIe devices in one node.5
  • NPS=0 — one domain for the entire system across both sockets, all channels interleaved into a single address space.5
  • Cache as NUMA — maps each shared cache to its own node. A 12-CCD part can expose up to 12 nodes per socket.5
Enumeration discipline

AMD is explicit: software that needs to understand NUMA topology or core enumeration must use documented operating-system utilities rather than assumptions about internal ordering. Do not hard-code core lists derived from a different BIOS revision.5

Go deeper — Intel's modes, and the fallback that catches people outVendor detail

Intel frames the problem physically. As core, memory-controller and interconnect density grow on-die while geometry shrinks, the time to move data from one side of the die to the other increases. Sub-NUMA clustering exists to shorten those traversals.11

ModeBehaviourSoftware impact
UMA A single contiguous address space interleaved among all memory controllers; all cores have equal access.11 No way to optimise for nearest resources; a core may be served by a controller or cache slice on the opposite side of the die.11
Hemisphere / Quadrant Two or four domains. Every core still reaches all controllers, but a hash function routes each request to the closest memory controller within the same domain.11 No software changes required. Better than UMA, not as good as SNC. Quadrant is the default.11
SNC-2 / SNC-4 Two or four localisation domains. In SNC-2 a domain holds half the processors, half the cache banks, and one memory controller with its channels.11 Cores see lower cache and memory latency for in-domain addresses. Needs BIOS enablement, symmetric memory population, and NUMA-optimised software — meet all three and it is the best-performing mode.11
Asymmetric memory silently downgrades your mode

The mode the BIOS actually uses is dictated by memory symmetry. If symmetry cannot be met for Quadrant, Hemisphere is used; if there is still insufficient symmetrical memory, the system defaults to UMA.11 Adding or removing memory sticks can therefore change your NUMA behaviour without anyone touching a setting.

SNC does not shrink your cache

Every address has a unique location in the last-level cache and is never duplicated. Localisation applies only to addresses mapped to controllers in the same socket; remote-socket addresses are uniformly distributed across all cache banks regardless of mode. The entire socket cache capacity stays available to each core, and reported capacity is unaffected.11

Module 5

Where your network card lives

In one minute

Memory has a location. So does your network card.

Cards plug into slots on the motherboard, and each slot is wired to one specific processor. That wiring is physical. You cannot change it in software — only by moving the card to a different slot.

So the card's node is the fixed point. Cores and memory are movable. Find the card's node first, then arrange everything else around it.

One command tells you

# Find your network cards and their addresses [7]
lspci | grep -i ethernet

# Ask which node one of them belongs to [5][7]
cat /sys/bus/pci/devices/0000:85:00.0/numa_node
# prints: 1

That card belongs to node 1. Your software should run on node 1's cores and use node 1's memory. It really is that direct.

What the documentation says

The guidance is consistent and blunt across vendors:

  • "When inserting NICs into PCI slots always check the caption, such as CPU0 or CPU1 to indicate which socket it is connected to."7
  • "If you are using 2 or more ports from different NICs, it is best to ensure that these NICs are on the same CPU socket."7
  • "To get the best performance, ensure that the core and NICs are in the same socket."7
  • AMD states the same as a three-way rule: place cores, memory, and I/O devices in the same NUMA node.5
Remember Module 4

Changing the BIOS node setting changes which node a card reports. So the order of operations matters: set the BIOS first, then read numa_node, then place your software. Reading it before a BIOS change tells you about a machine that no longer exists.

Go deeper — slot bandwidth is a separate problemAdvanced

Correct placement in an under-provisioned slot fails just as thoroughly as misplacement.

# Confirm the link width and speed you actually got [7][8]
lspci -s 85:00.0 -vv | grep LnkSta
#  LnkSta: Speed 16GT/s, Width x16, ...

DPDK advises PCIe Gen3 x8 or x16 slots, because Gen2 does not provide enough bandwidth for two 10 GbE ports and above.7 AMD EPYC supports PCIe generations 1 through 5 depending on the processor family, and the guidance is to use slots that provide adequate bandwidth.8

DPDK's AMD platform guide lists overall performance as influenced by BIOS settings, NUMA per socket configuration, memory per NUMA allocation, and proximity to I/O devices.8 For a complete picture of cores and cards per node in one output, use lstopo-no-graphics.5

Module 6

SR-IOV — one card pretending to be many

In one minute

SR-IOV lets a single physical network card present itself to the system as many separate cards. Each virtual copy can be handed to a different virtual machine, container or application, and each one gets near-native speed.

The real card is called the Physical Function. The virtual copies are Virtual Functions.

The NUMA point: the virtual copies are not real hardware. They are still the one physical card, in the one physical slot, attached to the one node. Every virtual copy inherits the real card's node.

Why this catches people out

Creating 64 virtual functions feels like spreading load across the machine. It is not. It is 64 consumers all funnelling through one card in one slot.

If you hand those virtual functions to workers spread across both processors, you have not distributed anything. You have multiplied the number of long trips by 64.

The rule

Check numa_node on the physical card — not on the virtual functions — and place the consumers of those virtual functions on that node.

Go deeper — what SR-IOV is technically, and the IOMMUAdvanced

SR-IOV is a PCI Express Extended capability that makes one physical device appear as multiple virtual devices. Virtual Function allocation is controlled dynamically by the Physical Function through registers in the capability. The feature is off by default, and until enabled the PF behaves as a traditional PCIe device. Once on, each VF has its own PCI configuration space accessible by its own Bus/Device/Function routing ID, plus its own memory space mapping its register set — so a VF driver operates on that register set and the VF appears as a real PCI device.4

The kernel treats VFs as hot-plugged PCI devices; they work like real PCI devices and need a driver as a normal PCI device would.4

# Recommended method for new devices: sysfs [4]
echo 8 > /sys/bus/pci/devices/0000:85:00.0/sriov_numvfs

# Disable
echo 0 > /sys/bus/pci/devices/0000:85:00.0/sriov_numvfs

# Stop the host binding a driver to VFs before creating them [4]
echo 0 > /sys/bus/pci/devices/0000:85:00.0/sriov_drivers_autoprobe

The IOMMU and passthrough mode

  • DPDK's Intel guidance: disable virtualization options when testing the physical function, and turn on VT-d if you want to use VFIO; add iommu=pt intel_iommu=on to the boot line.7
  • AMD's guidance: place the IOMMU in passthrough mode — iommu=pt amd_iommu=on — to improve host performance. AMD recommends enabling IOMMU in BIOS; it lets operating systems provide additional protection for DMA-capable devices.5
  • DPDK exposes --iova-mode <pa|va>, plus --vfio-intr and --vfio-vf-token for VFIO-bound devices.9
Why passthrough mode does not solve NUMA

Passthrough removes per-transaction address remapping from the DMA path. That is a constant-factor win applied everywhere equally. It does not shorten the physical distance a DMA write travels to reach a remote node's memory. NUMA placement is a path-length win. You need both.

Where this is heading

Intel positions Scalable I/O Virtualization as replacing SR-IOV: instead of a complete virtual function interface, it uses lightweight assignable device interfaces optimised for fast data-path access from the guest, interfacing with PCIe or CXL via Process Address Space IDs.11 The NUMA arithmetic is unchanged — it is still one physical device on one slot.

Module 7

Hugepages

In one minute

Memory is handed out in fixed-size blocks called pages. The normal size is tiny — 4 kilobytes.

The processor keeps a small lookup table so it can find pages quickly. With 4 KB pages, that table fills up fast, and every miss costs time.

Hugepages are the same memory in much larger blocks — 2 megabytes or 1 gigabyte. Fewer, bigger blocks means far fewer lookups.

The NUMA connection: hugepages are allocated per node. If you ask for them carelessly, they can all land on the wrong node — and Linux will not tell you.

Why the size matters so much

The lookup table is called the TLB. The kernel documentation describes it as "typically a very scarce resource on processor."3 It has room for a limited number of entries, and each entry covers one page.

So the amount of memory the processor can find quickly depends on your page size. Same number of entries, much bigger pages, far more reach.

Mapping the same amount of memory with 2 MB pages instead of 4 KB pages needs 512× fewer lookups. With 1 GB pages, 262,144× fewer. x86 processors support 4 KB and 2 MB pages, and 1 GB where the architecture allows it.3

The second benefit: they stay put

Normal memory can be moved or swapped out to disk when the system is under pressure. That causes sudden, unpredictable pauses — terrible for packet processing.

Hugepages are reserved by the kernel, cannot be used for anything else, and cannot be swapped out under memory pressure.3 Your memory stays exactly where you put it.

The trap

The silent skew — this is the important part of this module

When you ask for hugepages at boot, Linux spreads them across nodes. But if a node does not have enough contiguous free memory, that node is "silently skipped." Linux then "attempt[s] to make up the difference by allocating extra pages on other nodes" that do have room.3

So you ask for 24 hugepages and get 24. Success. Except node 2 got zero and node 0 got twelve. Nothing failed. Nothing warned. Your software on node 2 then either cannot find memory, or quietly gets served from a node that is not its own — and you spend a week blaming the network card.

How to avoid it

# Ask for a specific count on each node, explicitly [3]
hugepagesz=1G hugepages=0:8,1:8,2:8,3:8

# Then ALWAYS check what you actually got [3][5]
cat /sys/devices/system/node/node*/meminfo | grep Huge

Two lines. The first asks properly. The second verifies. Never skip the second.

How hugepages help the NUMA outcome
  1. Fewer lookups — and a failed lookup on a remote node is itself a remote memory access, so you cut traffic you never counted.
  2. Big contiguous blocks — a 1 GB pool backed by one page is guaranteed to sit in one node's memory. The same pool made of 262,144 small pages can get scattered.
  3. No swapping, no surprise pauses — so what you measure reflects your layout, not random memory-management noise.3
  4. Per-node visibility — you can audit placement before starting the application.3
And where hugepages make things worse

Big pages are a blunter unit. If a node's pool runs out, a 1 GB request cannot be partly satisfied locally — it goes remote entirely, or fails. Coarse granularity turns a gentle slowdown into a cliff. Size each node's pool deliberately rather than letting the kernel spread a single global number for you.

Go deeper — policy interaction, vendor settings and the demote interfaceAdvanced

Three ways to control placement, plus one from DPDK

# 1. Per-node counts at boot [3]
hugepagesz=1G hugepages=0:8,1:8,2:8,3:8

# 2. Per-node sysfs — ignores mempolicy and cpuset constraints [3]
echo 8 > /sys/devices/system/node/node2/hugepages/hugepages-1048576kB/nr_hugepages

# 3. Policy-aware allocation [3]
numactl -m 2 echo 20 > /proc/sys/vm/nr_hugepages_mempolicy

# 4. Verify [3][5]
cat /sys/devices/system/node/node*/meminfo | fgrep Huge
dpdk-hugepages.py -s

Note the asymmetry: writing nr_hugepages ignores mempolicy; writing nr_hugepages_mempolicy honours the writing task's NUMA memory policy.3 Writing the per-node sysfs attribute adjusts that node's count regardless of the task's mempolicy or cpuset constraints.3

Also: under a memory policy, hugepages are distributed as if "interleave" had been specified, and if a node in the policy lacks sufficient contiguous memory the allocation will not fall back to a neighbour — deliberately, to avoid imbalancing the pool.3

Boot-time allocation is described as the most reliable method because memory has not yet become fragmented.3 A 1 GB page can be split into 512 × 2 MB pages via the demote interface.3

DPDK adds a complementary measure: the OS may load and unload memory pages at its own discretion, and those loads hurt because the process waits while the kernel fetches them — so pre-load and lock with mlockall(MCL_CURRENT | MCL_FUTURE).6

Module 8

DPDK and the one rule

In one minute

DPDK is a toolkit for processing network packets very fast. It works by bypassing the operating system's normal networking and letting an application talk to the network card directly.

Instead of waiting to be told a packet arrived, a DPDK program constantly checks for new packets on a dedicated core. This is called poll mode, and it is why DPDK reaches speeds normal networking cannot.

Because DPDK manages its own memory, it also has to make its own NUMA decisions. It gives you the controls — but it will not choose for you.

The one rule

Straight from the DPDK troubleshooting guide

"The NUMA instance for packets or objects from NIC, mempool, and ring should be the same." The accompanying diagram is captioned "Memory objects have to be close to the device per NUMA."12

In plain terms, three things must agree on which node they are in:

  • the network card — fixed by its slot;
  • the memory pool the packets are stored in — you choose this;
  • the queue the card and software pass packets through — you choose this too.

Add the polling core to that list and you have the whole discipline. Four things, one node.

The settings that do it

# Run on cores 8 to 15 (pick cores that are on your card's node)
-l 8-15

# Reserve 4 GB of memory on node 0, and none on node 1 [9]
--numa-mem 4096,0

# Only use this specific network card, ignore the others [9]
-a 0000:41:00.0

Those three options carry most of the benefit. Everything else is refinement.

Go deeper — the full EAL parameter set and coding guidanceAdvanced

DPDK states the principle directly: "On a NUMA system, it is preferable to access local memory since remote memory access is slower. In the DPDK, the memzone, ring, rte_malloc and mempool APIs provide a way to create a pool on a specific socket."6 The mempool library specifically provides object alignment, lockless access, NUMA awareness, bulk operations and a per-core cache.6

Two traps in core assignment

DPDK warns that binding multiple lcores to a single physical CPU "can cause problems with poor performance or deadlock when using DPDK rings or memory pools or spinlocks. Such a configuration should only be used with care."9

Also note that a mapping like '(1-3)@(31-33)' lets three threads float across three CPUs as the OS decides.9 Floating threads are how carefully-placed memory becomes remote at runtime.

Memory channels and object spreading

Each channel has a bandwidth limit, so concentrating all accesses on the first channel is a bottleneck.6 By default the mempool library spreads object addresses among memory channels using padding, so each object starts on a different channel and rank — valuable for packet buffers where only the first 64 bytes are touched.610

Connect this back to Module 4

Channel spreading assumes the channels are local. The BIOS node setting determines how many channels interleave within a node.511 Changing that setting silently changes what -n should be and how much parallel bandwidth one node's pool can reach.

Other guidance worth knowing

  • Do not use standard C library functions in the fast path. memcpy() and strcpy() are not designed for performance; use rte_memcpy(). Avoid malloc-style allocation in the data path — managing a fragmented heap is costly.6
  • Avoid partial writes. When devices write to memory through DMA, it costs less if the write covers a full cache line.6 A costlier write across a remote path pays both penalties.
  • Prefer per-core variables. Read-write access by several cores to the same memory generates costly cache misses.6 Coherency traffic crosses the same link your packets do.
  • Duplicate read-mostly data. DPDK explicitly suggests duplicating data to optimise speed on a NUMA system.6
  • Batch size is a dial. Processing packets in batches (default 32) spreads the cost of notifying the card across many packets; a batch of 1 gives lower latency at lower throughput.6
Module 9

Following one packet

In one minute

Everything so far comes together here. Watch a single packet travel through the server, first with everything in the right place, then with the memory and cores on the wrong node.

The lesson: one placement mistake does not cost you one penalty. It costs you several, because the packet crosses back and forth repeatedly.

Why it crosses so many times

1
The card writes the packet into memory. If that memory is on another node, that is one crossing — before the software has even seen it.
2
The core reads the packet to look at it. Remote memory again. Second crossing.
3
The core tells the card it is finished, by writing to the card. The card is on the other node now. Third crossing.
4
The memory is handed back to the pool for reuse. Remote once more. Fourth crossing.

Four crossings, per packet, at millions of packets per second. That is how a 100 gigabit card ends up delivering 40.

Why this shows up as inconsistency, not just slowness

The link between nodes has a fixed, shared capacity. As cross-node traffic grows, queuing on that link grows faster than the traffic does. The result is that your worst packets get much worse, faster than your average packet does.

For a network application, that inconsistency is usually a bigger problem than the average.

Go deeper — the mechanics of each crossing, and a calibration pointAdvanced
  1. DMA descriptor fetch. The card reads its receive queue. If that queue was allocated on a node other than the one hosting the card's root complex, that read crosses the link before any packet data moves.
  2. DMA packet write. The device writes packet data into a buffer from the pool. DPDK creates pools on a specific socket for exactly this reason; card, pool and queue should share a NUMA instance.12 Partial cache-line writes cost more than full ones, compounding it.6
  3. Notification write. The core writes to the device across PCIe. DPDK notes this cost explicitly and spreads it across a batch.6
  4. Core read. The polling core touches the packet header — a remote memory access if the buffer is remote.6
  5. Cache behaviour. Under SNC, addresses mapped to remote sockets are uniformly distributed across all cache banks rather than localised, so remote traffic loses the locality benefit SNC provides.11
  6. Buffer return. Freeing writes back into the pool — remote again, now contending with the coherency traffic from steps 2 and 4.
A calibration point from AMD's own testing

On EPYC 9004 with a vector-mode driver at 100 Gbps and 64-byte packets: 90–95 Mpps with 1 core and 3 queues; 145 Mpps with 8 cores and 8 queues; 149 Mpps with 10 cores and 13 queues.5 Those figures come from a guide whose configuration section requires cores, memory and I/O in the same NUMA node.5 Treat them as what correct placement buys on that platform, not a promise for an arbitrary system.

Module 10

The checklist

The whole training, in five steps
  1. Find your network card's node. It is the fixed point — everything else moves around it.
  2. Pin your software's threads to cores on that node, so they cannot drift.
  3. Allocate hugepages per node and check what you actually got. Never trust a global number.
  4. Tell your application which node to use for its memory pools and queues.
  5. Re-check everything after any BIOS change, because the node numbers may have moved.

The commands, in order

# 1. What does this machine look like?
numactl --hardware
lstopo-no-graphics

# 2. Which node is my network card on?  [5][7]
lspci | grep -i ethernet
cat /sys/bus/pci/devices/0000:85:00.0/numa_node

# 3. Did my hugepages land where I asked?  [3][5]
cat /sys/devices/system/node/node*/meminfo | grep Huge

# 4. Run pinned to that node  [9]
./myapp -l 8-15 --numa-mem 4096,0 -a 0000:41:00.0
If you remember one thing

Find the card's node. Put the cores, the memory and the software on that same node. Verify rather than assume. That single habit prevents most of the problems in this training.
